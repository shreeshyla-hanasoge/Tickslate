### Added

- Per-widget entries: `tickslate/elements/grid`, `card`, `metric`, `chart`, `today-pnl`, `equity-curve` and `session-clock`. Each registers only its own tag and exports its class and types, so `import 'tickslate/elements/metric'` no longer pulls in every widget. `tickslate/elements` still registers everything and exports the same names.
- A one-script bundle for pages with no build step: `<script src="…/cdn/tickslate.iife.js">` sets `window.Tickslate` (every export of `tickslate` and `tickslate/elements`) and registers all elements. `cdn/tickslate.js` is the same code as a minified ES module. Both are production builds, with no development warnings, and the IIFE adds `Tickslate` to the page's globals and nothing else. Use the bundle or the package entries, not both: each carries its own core, so loading both gives a page two registries and two `configure()` states; and the bundle and the core-only UMD both set `window.Tickslate`.

### Changed

- The `unpkg` and `jsdelivr` fields now point at the all-in IIFE (`cdn/tickslate.iife.js`) instead of the core-only UMD, so a bare unpkg or jsDelivr script tag gets a working dashboard. `window.Tickslate` still carries every core export. `umd/tickslate.umd.js` is unchanged and still ships.
- The `development` export condition now resolves into a parallel `dev/` tree (`dev/elements.js` and `dev/elements/<name>.js`) that replaces `elements.dev.js`. It shares the one core `index.js` with the production files, so `configure()` state is the same whichever a host loads.

### Internal

- `src/elements/define/<name>.js` calls the shared `define()` for one tag and re-exports its class; `src/elements/index.js` imports them all. `vite.lib.config.js`, `vite.dev.config.js` and `scripts/pack-lib.mjs` find the modules by listing `src/elements/define/`, so a new widget is one file. The listing and the naming rule live in the new `scripts/entries.mjs`, which is not in the story's file list: three consumers would otherwise each carry a copy.
- `scripts/pack-lib.mjs` generates `exports`, `typesVersions` and `sideEffects` into `dist-lib/package.json` and writes a declaration stub per entry (`elements/<name>.d.ts`) that re-exports from `elements.d.ts` and `grid.d.ts`. `package.lib.json` keeps only the hand-written fields (`.`, `./tokens.css`, `./package.json`), and `unpkg` and `jsdelivr` move to the IIFE.
- `vite.cdn.config.js` builds `dist-lib/cdn/tickslate.js` and `tickslate.iife.js`, as a plain (non-library) build with two outputs, because library mode leaves an ES file's whitespace in and nothing downstream bundles these files. New script `build:cdn`, added to `release` after `build:umd`; `vite.umd.config.js` only has its comment changed.
- The IIFE is wrapped in one function (`vite.cdn.config.js`), because esbuild's class-field helpers otherwise land outside it as globals; `verify-package` runs the IIFE and the UMD in a `vm` and asserts each adds exactly one global, `Tickslate`. The CDN files are built without source maps, so none are published for them (`sourcemap: false`, nothing to exclude).
- Every per-widget declaration stub also exports the shared widget types (`WidgetFreshness`, `ViewModelContext`, `WidgetState`), and `pack-lib` fails if any type in `elements.d.ts` is exported by no stub, so a new widget's types are placed on purpose (`TYPE_EXTRAS`). `describeEntry` throws on a define module it can read no tag or export from, so the tree-shaking checks cannot pass with nothing to compare. The playground and site aliases answer `tickslate/elements/<name>` from the define modules.
- `scripts/verify-package.mjs` asserts each entry has `types`, `development`, `import` and `default` in that order, that each `import` target has a twin under `dev/`, that production and development files never import each other and share the one `index.js`, that no production or CDN file contains `console.warn`, that every entry resolves to its file with and without `--conditions=development`, that each entry's esbuild bundle (production and development) registers only its own tag, and that the IIFE sets `window.Tickslate` and registers every element when run in a fake-DOM `vm` context.
- `scripts/check-size.mjs` budgets each `tickslate/elements/<name>` entry, bundled with its core and chunks, at its measured min+gz size plus 10 %, rounded up to 0.5 kB (measured 2026-10-14: grid 20,664 B, card 11,168 B, metric 12,910 B, chart 13,865 B, today-pnl 13,567 B, equity-curve 13,720 B, session-clock 12,868 B). An entry with no budget fails the run. The all-in `tickslate/elements` and the two CDN files are reported only (RFC 0003 Decision 38); the old 50 kB figure is gone.
- `test/entries.test.mjs` uses a fake `customElements` to assert each define module registers exactly its own tag and exports the class it registered, and that the all-in entry registers all of them. `test/docs-coverage.test.mjs` now also reads `src/elements/define/` when it looks for `define()` calls, which moved there; it is outside the story's file list but fails otherwise.
- Differences from RFC 0003 that the maintainer should know about:
  - **Grid plus one widget at 15 kB cannot be met, so it is a warning, not enforced (§25).** The grid alone is 20,664 B min+gz bundled (16,461 B as the single built file, core excluded), so every pair is 29 to 32 kB. The six `grid + <widget>` rows carry the 15 kB figure in mode `warn` and print their overage each run. A widget adds 9 to 12 kB on top of the grid, so the figure may have been meant per widget, or the grid has to shrink. This needs a decision, not a code change here.
  - **The tree-shaking check cannot be "no `ts-grid` or `ts-equity-curve` string" (§2.4).** Those strings stay in every bundle through code that is not registration: the core `WIDGETS` catalog (`ts-equity-curve`), the not-yet-defined CSS in `default-tokens.js` (every tag) and `localName === 'ts-grid'` in `widget.js`. Removing them means editing widget and core files, which this story does not own. The check asserts instead that a bundle holds a `define()` call for its own tag and no other, and none of another widget's class, in production and development bundles.
  - **The chart's entry name is applied in the build, not in pack-lib (§2.1, §29.2).** `series-chart` is mapped to `chart` in `scripts/entries.mjs`, which names the built file `elements/chart.js`; renaming the file after the build would break the chunks that import it.
  - **`sideEffects` also lists `./cdn/*.js` (§2.2)**, since both CDN files register elements and a bundler must not drop an import of one.
  - **"Every `import` export has a `development` one" is checked for the elements entries only (§2.2).** The core (`.`) has no development build by design: both trees import the single `index.js`.
