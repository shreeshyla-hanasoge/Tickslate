### Added

- `tickslate/jsx`, `tickslate/vue` and `tickslate/svelte`: types-only entries that add every `ts-*` tag to React's `JSX.IntrinsicElements`, Vue's `GlobalComponents` and Svelte's `svelteHTML.IntrinsicElements`, with each tag's attributes and a typed `data`. Add `import type {} from 'tickslate/jsx'` (or `vue`, `svelte`) once; nothing is loaded at runtime. They resolve under `moduleResolution` bundler, node16 and node10.
- `TsCommonAction`, `TsCardAction`, `TsMetricAction`, `TsChartAction`, `TsTodayPnlAction`, `TsEquityCurveAction` and `TsSessionClockAction`: the `ts-action` detail of each element as a union, exported from `tickslate/elements` and the element's own entry, along with `TsOpenAction` and `TsChartSelectAction`. `addEventListener('ts-action', …)` on each element is typed to its union, so `e.detail.action === 'range'` on a metric is a compile error.
- `custom-elements.json` (a Custom Elements Manifest) and `vscode.html-custom-data.json` (VS Code's HTML custom data) ship in the package, listing every tag with its attributes, properties, events, parts and slots. The package's `customElements` field points at the first; both are exported as `tickslate/custom-elements.json` and `tickslate/vscode.html-custom-data.json`.

### Changed

- `TsCard`'s `spec` is declared as a property, not an accessor, matching `TsWidget`. TypeScript with `skipLibCheck` off reported the accessor as an error in `elements.d.ts`.

### Internal

- `scripts/gen-manifest.mjs` writes both manifest files from the declaration files with `node:fs` only: a JSDoc block with `@element ts-tag` (and `@attr`, `@fires`, `@csspart`, `@slot`, `@cssprop`) documents a tag, a block with `@base TsWidget` documents what every widget inherits, and the exported classes supply properties and methods. `pack-lib` runs it, and it fails the build for a tag that a `src/elements/define/` module registers and no block documents. A story that adds an element writes its `@element` block, and its line in `TsElementAttributes` if it has attributes of its own, in its `.d.ts`; no list in a script changes.
- `src/types/{jsx,vue,svelte}.d.ts` share `src/types/common.d.ts`, which reads the tag list from `HTMLElementTagNameMap` and each tag's attributes from `TsWidgetAttributes` and `TsElementAttributes` in `src/elements/index.d.ts`. `pack-lib` ships them under `types/`, finds them by listing `src/types/`, gives each export a single `types` condition and a `typesVersions` path, and refuses one that imports a framework without `import type`.
- `scripts/check-types.mjs` (`npm run check:types`, also `test:types`) links `test/types/node_modules/tickslate` to `dist-lib/` and compiles the fixtures in `test/types/` under `tsconfig.bundler.json`, `tsconfig.node16.json` and `tsconfig.node10.json`, all extending the root `tsconfig.json`. Each fixture has `@ts-expect-error` lines on wrong data keys, sizes and ranges; TypeScript reports an unused one as TS2578, so a type that goes loose fails the run. CI runs it in the build job after `npm run release`; run `npm run release` first locally.
- New dev dependencies, none in `package.lib.json`: `typescript` 5.9.3 (the 5.x line, because TypeScript 6 deprecates and 7 removes `moduleResolution: node10`, which RFC 0003 §22.3 requires checking), `@types/react` and `vue`, which the React and Vue fixtures resolve their augmentations against.
- `test/manifest.test.mjs` runs the generator on `src/` and on a temporary tree that gains an element, checks the tag, attribute, event, part and slot lists, that an undocumented tag throws, and that `TsWidgetAttributes` and `TsElementAttributes` agree with the `@attr` lines.
- Differences from RFC 0003 that the maintainer should know about:
  - **"The generator fails when a tag in `WIDGETS` has no tag documentation" applies to tags a define module registers.** `WIDGETS` lists six tags with no element yet (`ts-pnl-calendar`, `ts-edge-stats`, `ts-capital-funding`, `ts-open-positions`, `ts-watchlist`, `ts-mini-chart`), so failing on all of them would fail every build today. The generator fails for each tag a `src/elements/define/` module registers, which is the same set once those widgets exist, and prints a note listing the catalog tags that have no module yet.
  - **`<ts-grid>`'s tags are documented in `src/elements/index.d.ts`**, in a block of their own, because `grid.d.ts` is not in this story's files. The generator finds the class from `HTMLElementTagNameMap` and reads the prose and members from `grid.d.ts`. The attributes, events, parts and slots common to every widget are likewise a `@base TsWidget` block in `index.d.ts`, since `widget.d.ts` is not this story's either.
  - **`§22.2`'s unions have `TsCommonAction` shared by `retry` and `open`**, and `TsOpenAction` and `TsChartSelectAction` are declared in `widget.d.ts` (tile-activation) and re-exported from `index.d.ts`. `<ts-table>`, `<ts-capital-funding>`, `<ts-watchlist>` and `<ts-open-positions>` do not exist yet, so their unions come with their stories.
  - **Static members are not in the manifest**, only instance fields and methods. Events on the framework typings are typed from `HTMLElementEventMap` (the loose `ts-action` detail), not per element; the per-element union is on `addEventListener`.
  - **Outside the story's file list:** `scripts/check-types.mjs`, `scripts/verify-package.mjs` (allows a types-only export, `types/*.d.ts`, the `customElements` field, and checks both manifest files list every tag), `test/manifest.test.mjs`, `test/types/vue.ts`, `test/types/svelte.ts`, `test/types/tsconfig.*.json` and `src/types/common.d.ts`.
