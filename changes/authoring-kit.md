### Added

- `defineWidget(tag, Class, { type })` registers your own widget with one call: it defines the element and records the class's `static spec` (label, sizes, `phoneRows`, and the optional `description` and `category`) in the widget catalog under `type`, as a snapshot taken at the call. Without a DOM it still records, and only skips defining the element.
- `defineWidget` does nothing when called again with the same class, tag and type. A module that is evaluated twice makes a new class, which throws, so guard the call with `if (!widgetCatalog()[type])`.
- `defineWidget` throws a `TypeError`, and records and defines nothing, for a missing `type`, a built-in key such as `'todayPnl'`, a class with a `catalogKey` (set or inherited from a built-in), a type another class recorded, a tag recorded under another type or owned by another class, a class already recorded under another type, the same class and type under a second tag, and a spec with no valid size.
- `widgetCatalog()` returns a frozen merge of the built-in `WIDGETS` and every registered widget, the same object until the next registration.
- `onCatalogChange(fn)` calls `fn(type)` after each registration and returns a function that stops it. A listener that throws is logged with `console.error` and skipped, so the others still run and the registration stands.
- `linePaths`, `scale` and `escapeHtml` are exported from `tickslate/elements`, with declarations, and are stable for 0.x: the chart geometry the built-in widgets draw with, and an escaper for markup built from data.
- A custom widgets guide builds a complete widget, from `static spec` to `defineWidget`, with a worked example and its tests: a template with no English in it, a pure `viewModel`, numbers that change in place, `emit`, loading, empty and error states, `dataShape`, `fit()`, translatable messages under your own keys, and a direction of change that holds in right-to-left locales.

### Internal

- `defineWidget`, `widgetCatalog` and `onCatalogChange` live in `src/elements/registry.js`, over a module-level `Map`, so two imports of one bundle share it. The grid does not read `widgetCatalog()` yet; the picker story switches its third source from `WIDGETS` (RFC 0003 §3).
- `npm test` also runs `examples/custom-widget/*.test.mjs`, so the existing CI `test` job (no install) covers the example. The acceptance text names `node --test examples/custom-widget/`, but Node 24 reads a bare directory as a module to run and fails, so the shell-expanded glob that `npm test` already uses is what runs.
- `examples/custom-widget/mrr.test.mjs` carries its own fake DOM (about 100 lines, trimmed from `test/fake-dom.mjs`), because the example's tests may import only `src/` and `node:*` and nothing in `src/` fakes a DOM. Its `querySelector` resolves only the `data-k` and `data-action` names present in the markup. A test also fails when a code block in the guide headed `// mrr.js` stops matching the file.
- Candidate for a later RFC amendment: **custom widgets can't register default messages.** `t` falls back to `EN` and then to the bare key, so a custom key with no host override renders as the key. `mrr.js` therefore carries a frozen English table of its own and uses `t`'s answer only when it is not the bare key, with plurals from `t(key, params, count)` and `Intl.PluralRules('en')` as the fallback. Something like `defineWidget(tag, Ctor, { type, messages })` would let the library do this once and let `t` fall back to it.
- Differences from RFC 0003 §3, for the documentation story:
  - **The spec is validated at registration, in `registry.js`**, by the same rules as the element's own `spec` getter in `widget.js` (sizes filtered to valid size names, `phoneRows` to positive integers by size), except that an empty size list throws, as §3 requires, where the getter degrades. The copy is deliberate: `widget.js` belongs to another story and does not export its validator, which works on an element, not a class.
  - **`defineWidget` rejects a class with a `catalogKey`**, which the RFC does not mention: such an element reads the built-in's spec, so the catalog would describe a widget the element is not.
  - **`linePaths`'s `maxPoints` is declared but not applied.** §3.1 lists it, and §23 (the performance story) implements the downsampling in `chart.js`, which this story does not own. The declaration says so; until then every point is drawn.
  - **`WidgetSpec` in `src/core/index.d.ts` has no `description` or `category` yet**, so `widgetCatalog()`'s `WidgetCatalog` type does not show them, though the recorded objects carry them. §18.1 adds them with the picker, in a file this story does not own. `TsWidget`'s declared `static spec` in `widget.d.ts` lacks them too, so a TypeScript author gets no completion for them.
  - **The declarations are written inline in `src/elements/index.d.ts`**, with no exported option types, so the check in `scripts/pack-lib.mjs` that no type is reachable only from the all-in entry needs no change. `escapeHtml` is declared again there (it is also in `widget.d.ts`) so the all-in entry names all three helpers.
